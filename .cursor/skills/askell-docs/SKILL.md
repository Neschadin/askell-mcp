## Fetch strategy

1. Fetch https://docs.askell.is/llms.txt if the index may have changed. Also open pages those docs link that the index still omits (`coupons.html`).
2. Fetch the **specific page** for the flow you are implementing (not the whole site).
3. Path/method/schema: bundled `spec/openapi-v*.json`, then overlays in this repo. Prose + captured payloads beat OpenAPI for flows swagger omits (embedded `askell.js` cart / session sub-paths, 3DS iframe, most webhook bodies). Bundled spec beats prose when swagger moved first: finalize payment-method rules, bank claims (`GET /v2/claim-rules/`, `GET /v2/claim-templates/`, `V2BillingRun.claim`, `POST .../cancel-claim/`, `POST .../change-claim/`, `cancel_open_claims`), `POST /payments/{uuid}/cancel/`, `GET|PUT|PATCH /plans/{planId}/` shared `payment_processor`, `service_entitlement_policy` on contract PATCH, customer portal (`customer-portal-entries` / `customer-portal-sessions`), `one_off_purchases` / `pending_delivery_change`, v1 `POST /subscriptions/quote/` and string `discount.id`, and interval-change retry abandonment (`change-anchor` spec text says an interval change whose payment failed is abandoned, whereas the live V2 page still says a manual retry applies it). Request body schema beats the operation description when they disagree (`V2SubscriptionContractPatch` vs the PATCH description).
4. Cite the page URL. Do not dump the whole page into chat.

## Known traps (docs vs OpenAPI)

- Auth: `Authorization: Api-Key <key>`. Public key is browser-safe for a few endpoints only. Exception: v1 `POST /subscriptions/{id}/apply-code/`, `GET .../discount/`, `POST .../remove-discount/` are `security: []` — `subscription_token` (`Subscription.token`), no API key. MCP `apiKeyKind` is `none` (omit `Authorization`).
- New integrations: V2 (`/v2/`). v1 is PlanVariant + Subscription.
- v1 plans (`/plans/{planId}/` GET/PUT/PATCH, secret): each entry in `/plans/` is a `PlanVariant` (`interval`, `interval_count`, `amount`, `currency` belong to that variant), while `payment_processor` belongs to the parent `Plan` — setting it changes `payment_processor` for **every** variant of that plan. Sending a numeric processor `id` alone on a claim processor (`type: claim`) clears `claim_rule_id` and `claim_template_id` to account defaults; pass `{ id, claim_rule_id, claim_template_id }` (both ids or neither) to set them, or omit `payment_processor` to keep current settings.
- Typical V2: catalog → quote → payment-processor-options → checkout → finalize → poll billing run.
- Quotes: pass `customer` (numeric id) when the buyer already exists, else combo discounts from their other active contracts and promo-code customer restrictions are skipped. First-period totals already include coupon + combo. `quote.recurring_*` include combo, **not** the coupon — renewal-with-coupon is `discount.recurring_final_amount` while duration still applies (`once` → after first payment use `recurring_*`). Combo is automatic, not `apply-code`. A coupon limited to products or prices discounts only lines in scope (a listed price, or any price of a listed product). The code is refused when none of the offer's prices is in scope. A plans-only or plan-variants-only coupon is refused on a contract quote.
- `finalize`: recurring offer needs a verified payment method even when due-now is 0 (trial / 100% off first period). Only a free one-time purchase finalizes without one. Live V2 page still says “unless 0 ISK” — bundled OpenAPI is right.
- Hosted `POST /v2/checkouts/`: `shipping` is required when the offer has physical products and the account has shipping options. No shipping-options list in OpenAPI (option ids are account config). Snapshot is `contract.shipping_selection` (plus `location` / `zone_name` / `weight_band`), not `V2Checkout`. Rate-table option with no zip/weight rate: `400`, `shipping_code=shipping_not_available`. Quote/checkout totals already include `shipping_fee` when present. Embedded widget collects address/shipping.
- Coupons: catalog CRUD is `/v2/coupons/` and `/v2/promotion-codes/` (secret). Coupon = discount definition; promotion code = customer-facing code. Create: exactly one of `amount_off`+`currency` or `percent_off`; `duration_in_months` iff `duration=repeating`. Redeemed coupon/code cannot DELETE — retire coupon with `redeem_by`/`max_redemptions`, promo with `active=false` (frees `code`). Contract still uses `POST .../apply-code/` `{promotion_code}` (one active). Scope: `applies_to_plans` (legacy plan ids, all variants), `applies_to_plan_variants` (one legacy variant), `applies_to_products` (catalog product ids, all prices), `applies_to_prices` (one catalog price id from `GET /v2/catalog/prices/`, also an offer item's `price`). All four empty applies to everything; once any list has an entry, only what is listed applies (plans-only or plan-variants-only gives nothing on contracts; products-only or prices-only gives nothing on legacy subscriptions). On a contract, `percent_off` is that percentage of in-scope lines and `amount_off` is at most their total. Switching an item to an unlisted price drops the discount. PATCH: omit a list to leave it, `[]` clears it. `contract.discount.coupon` does not include these arrays — `GET /v2/coupons/{id}/`. Live https://docs.askell.is/en/api/coupons.html wrongly says a coupon `restrictions` field can be cleared with null — OpenAPI puts `restrictions` on the promotion code (`minimum_amount` + `minimum_amount_currency`, or `{}` to clear), not on the coupon. Unknown coupon fields are `400`.
- v1 promotion codes are not `Subscription.discount` (0–100). First charge: `promotion_code` on `POST /customers/{ref}/subscriptions/add/` or each item of `POST /subscriptions/multi/`. `apply-code` does not discount the first charge. Hosted `POST /checkouts/` `promotion_code` requires a `plan`, redeems nothing, and is applied only when that checkout token is `payment_method.token` on multi (first item of that plan with no code of its own; unless `capture_only`, the discounted first charge must match the checkout amount). `add/` does not carry the checkout code. One discount, including a pending one (future `start_date`): `GET .../discount/` reports `has_discount: false`, `apply-code` is still 400. `discount.id` is a string (`di_…`), not an integer; those three paths are `security: []` (`subscription_token`). Preview: `POST /subscriptions/quote/` (secret; nothing stored/redeemed; see `spec/openapi-v1.json` for response schema).
- V2 `V2CustomerPaymentMethod.card`: `brand`, `last4`, `funding`. `null` for claim and invoice. `funding` is `null` for Teya, and for Valitor Pay until the card's first successful charge. Visa Electron is `visa`.
- Bank claims (`krafa`, secret): `GET /v2/claim-rules/` and `GET /v2/claim-templates/` list active claim rules and bank-registered templates (`G8` subscriptions, `37` invoices) ordered by id. When `claim_rule_id` / `claim_template_id` is omitted on `POST /v2/customers/{customerReference}/payment-methods/`, the first item in each list is used. On a `pending_external` `V2BillingRun` waiting on an open bank claim (`claim.state: sent_to_bank`, `claim.status: unpaid`), `run.claim` holds that claim and `run.transaction_id` is `null` until paid. `POST /v2/billing-runs/{id}/cancel-claim/` (no body): on an **active** contract the run becomes `failed_terminal` (`fail_code: claim_cancelled`), sending `billing_run.failed` + `payment.changed` and running failure emails/policy; on a **canceled/ended** contract the run becomes `canceled` (`claim_cancelled_contract_closed`), sending `billing_run.changed` + `payment.changed` without failure emails/policy. `202` means bank cancelled and Askell sync is pending — do not resend (duplicate concurrent call gets `502`). `POST /v2/billing-runs/{id}/change-claim/` `{ final_due_date: "YYYY-MM-DD" }` moves *eindagi* (not past, not after `claim.cancellation_date`).
- Contract `cancel_open_claims` (`POST /v2/subscription-contracts/{id}/cancel/`, default `true`): immediate cancellations only (ignored on `period_end` / future `cancel_at`). Cancels unpaid bank claims for unserved periods in the background (`metadata.claim_cancellation`). A prorated cancellation (`proration_behavior` other than `none`) keeps the claim of the period it falls in open because unused-time credit settles that period.
- Fulfillment: `GET /v2/fulfillment-orders/` and `GET .../{id}/` are warehouse reads (secret; same body as `fulfillment_order.*` = `V2FulfillmentOrder`). Mutate: `POST .../fulfill/` (optional body) and `POST .../cancel/` (no body). Idempotent `200` if already in that state (no second webhook/email). `409`: `order_cancelled` | `order_fulfilled` | `booking_in_progress`. External carrier: shipment `handler` is `""` — read `carrier`. `403` if contracts/shipping/fulfillment off. Poll `updated_since` after a missed webhook. Live webhook page names `created`, `shipment_booked` (extra `shipment_id`), `fulfilled`, `cancelled`. Do not invent `changed`.
- Hosted iframe (not `askell.js`): `allowed_origin` on `POST /v2/checkouts/` and payment-method-registrations (one origin, no path; `http` only localhost/loopback). Replaces account-level `frame-ancestors`. Rejected on `/v2/checkout-sessions/` — that uses sales-channel `allowed_origins[]`.
- Checkout/session metadata copies onto the contract at finalize except Askell-owned keys (`askell_source`, `billing_anchor_mode`, `activation_failure`, `email_markers`, `copied_legacy_pauses`, `copied_legacy_extra_data`, `migration_source`, `migration_cadence_mode`, `legacy_subscription_ids`, `seed`). On a shared key the session value wins. PATCH `metadata` replaces integration keys; those Askell keys keep their current values and are ignored if sent.
- Legacy writes: `400` `LegacySubscriptionGuardError`, match `code`. Not every v1 write — customer, webhook, and one-off payment writes are not this guard. `legacy_subscriptions_disabled` on contracts-only accounts (`POST /subscriptions/multi/` neither creates nor updates the customer, `POST /customers/{ref}/subscriptions/add/` also sends `status: error`, `POST /checkouts/` with a `plan`; processor checkout still works). `subscription_managed_by_contract` on PATCH/cancel/activate/set_expiry (`migrated_to_contract_id`, `v2_endpoint`).
- Contract `reference` & PATCH: `reference` is max 128, no commas, not unique (`?reference=` returns a list). Set `contract_reference` on `POST /v2/checkouts/` (no session) or `POST /v2/checkout-sessions/` (secret) so it is already on `subscription_contract.created` (a later PATCH misses that webhook; browser cannot set it). `V2SubscriptionContractPatch` allows ONLY `metadata`, `reference`, `payment_processor_override`, `sales_channel` (id or reference; `null`/blank clears), and `service_entitlement_policy` (`on_run_created` | `on_run_succeeded`; forward-only — open billing runs keep their creation policy, also settable on `POST /v2/subscription-contracts/`). The PATCH operation description and live V2 page also mention `delivery_address` / `accounting_department` / `accounting_cost_center`, which are **not** in `V2SubscriptionContractPatch` — do not send them.
- One-off purchases and delivery changes: `contract.one_off_purchases` is `pending` only. Every state is `GET /v2/subscription-contracts/{contractId}/one-off-purchases/` (`pending` | `billed` | `canceled` | `failed`; no `page_size` → one array). `pending_delivery_change` is a customer subscription-page address or shipping change made after the next order's edit cutoff, queued for the following order (`state`: `pending` | `applied` | `canceled` | `superseded`); `subscription_contract.changed` fires when queued, canceled, or applied. No create or cancel path for either.
- Scheduled changes: `operation` is `update_item` | `add_item` | `remove_item`. `add_item` has `contract_item` null until the renewal creates it; `remove_item` has `price` null. `group` is applied or failed whole (`failure_code` `group_failed`). A customer frequency switch is a group of `interval_change` rows, one per recurring item; canceling one cancels the others.
- Customer portal (secret, not the legacy token): `POST /v2/customer-portal-entries/` is a single-use hosted-page sign-in `url` (5 minutes, Continue click before it is spent, 60/min). `POST /v2/customer-portal-sessions/` is the on-site widget token (`Authorization: Customer-Session <token>`, never a URL; new token each page load; 30 minutes idle, 4 hours max; 300/min). Required `sales_channel`, `customer` xor `customer_reference`. `403` sessions can return `self_service_unavailable` (outside `V2CustomerPortalError.code`). Do not redact `url` or `token`. Not `subscriber_page`.
- Item changes: `apply_at=now` (default) rejects future `effective_at` (`future_effective_at_not_supported`). `apply_at=period_end` charges nothing now (`scheduled_change`) and cannot be combined with `effective_at` / `settlement_behavior` / `include_pending_adjustments` / `apply_on_payment` (`invalid_apply_at`). Pending scheduled change → `409` `scheduled_change_exists` until `POST .../scheduled-changes/{id}/cancel/`. Immediate interval change awaits payment (`pending_interval_change` + `pending_change`); a failed payment abandons it (retrying the run does not apply it — spec `change-anchor` text wins over live V2 page). `apply_on_payment` (`items/update` and `proration-preview`, `apply_at=now`, requires `invoice_now` → `apply_on_payment_requires_invoice_now`): same-interval sets only `pending_change`; preview token validates only an update with the same `apply_on_payment`.
- Anchor: `POST /v2/subscription-contracts/{id}/change-anchor/` (not PATCH `billing_anchor_at`). `new_billing_anchor_at` after `effective_at`, and with proration at most one billing period later. Does not extend entitlements. Preview: `proration-preview` `operation=change_anchor`.
- Refunds & Payment cancel: a billing-run charge is not a Payment (`payment.*` has v1 `transactions[]` vs v2 flat object with `Hook-API-Version: v2`, `billing_run_id`). Optional `{amount}` on every refund path; omit to refund everything left. `POST /v2/billing-runs/{id}/refund/` uses `refundable_amount`; partial stays `succeeded` with `refunded_amount` and sends `billing_run.changed`; `202` → do not resend immediately. `POST /payments/{uuid}/refund/` is one-off Payments only; `POST /transactions/{uuid}/refund/` is legacy subscription transactions (`{transaction, refund}`); both `400` `billing_run_charge` with `billing_run_id` for a V2 billing-run uuid. Unpaid one-off Payments cancel via `POST /payments/{uuid}/cancel/` (secret, no body; cancels unpaid bank claims first; idempotent `200`; `202` = bank cancelled, Askell sync pending, do not treat as failure; `409` `payment_settled` | `payment_not_cancellable`, `502` `claim_cancel_refused`).
- Webhooks: non-migrated `subscription_contract.*` is the GET contract (`customer` is an object; numeric id is `customer_id`). `migrated` is short and its `customer` is a number. A scheduled cancellation sends `ended`, not `canceled`, even though `state` becomes `canceled`. `subscription_contract_scheduled_change.*` and `subscription_contract_item.entitlement_changed` are separate registrations. Billing-run webhooks use `contract_id`, not `contract`.
- Embedded checkout: secret key creates a scoped session server-side; browser gets only the session token + `askell.js` (supports multi-page cart `mountProduct` / `mountCart` / `getSessionToken`). `V2CheckoutSession.status`: `completed` = paid or awaiting processor (`contract_id` and `initial_billing_run_id` set, not "contract active"); `expired` = `expires_at` passed with no payment in flight (do not finalize again).
- `checkout_url` on V2 checkout objects is the API URL, not a hosted payment page. `subscriber_page` on `V2SubscriptionContract` is the read-only customer management URL (`/change_contract/<token>/`), not a seller-verified portal link.
- Webhook body **is the event object**, not `{ event, data }`. HMAC-SHA512 of raw body (`Hook-HMAC`). `GET /webhooks/` returns plaintext `hmac_secret` on every list/get/create; MCP tool output redacts it.
- Two API hosts, same v1/v2 surface: production `https://askell.is/api` and sandbox `https://sandbox.askell.is/api` (isolated tenant; keys from that dashboard). Test Gateway is a payment acquirer on either host, not a separate API.

## Do not

- Copy the docs site into `spec/` or `src/resources/` as a snapshot of every HTML page.
- Put Askell prose into `mcp-docs` (that skill is protocol/SDK only).
- Invent coupon/checkout/webhook/shipping/fulfillment/claim shapes from training data. There is no shipping-options list in OpenAPI. Do not invent `fulfillment_order.changed`. Do not send PATCH fields that are only in an operation description (`delivery_address`, `accounting_*`); `sales_channel` and `service_entitlement_policy` are real PATCH fields. Do not treat `202` from `POST /payments/{uuid}/cancel/`, `POST /v2/billing-runs/{id}/cancel-claim/`, or refund endpoints as a failure or immediately resend. Do not invent a write path for one-off purchases or delivery changes. Do not redact customer-portal `url` / `token`, and do not put that token in a URL. Do not treat `subscription_contract.*` as including `subscription_contract_scheduled_change.*` or `subscription_contract_item.*`. Do not read a non-migrated contract webhook's `customer` as a number.
